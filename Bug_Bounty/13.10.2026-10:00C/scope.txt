# MForce Enhanced Framework — Bug Bounty Scope & Conditions

**Status:** Community vulnerability reporting is welcome. Financial rewards
are discretionary, depend on available funding and must be individually
confirmed by the project maintainers. **No automatic payout is promised.**

## Potential recognition

| Severity | Potential recognition |
| --- | --- |
| Critical | Up to €70, subject to prior confirmation and funding |
| High | Up to €70, subject to prior confirmation and funding |
| Medium | Public credit with consent; payment not promised |
| Low | Public credit with consent |

**Maximum possible monetary reward described by this document: €70
per accepted vulnerability.** This removes the previous contradictory
€70/€100 and Medium-reward wording; it does not create a funding
commitment or guarantee any payout. The final decision, amount and
payment method require private agreement.

## Authorized scope

- Source code of the current default branch of
  `GotUrBack-Public/MForce-Enhanced-Framework`.
- Local Bash/Python runtime, module input handling, update logic,
  official website source and configuration processing.
- Your **own** test installations and lab targets.

Excluded: GitHub and GitHub Pages platform security, third-party
websites or APIs, RDAP providers, other people's installations,
unrelated repositories, cloud infrastructure and unapproved targets.

## Eligible reports

A report should show independently reproducible impact caused by a
project vulnerability, such as command injection, unauthorized file
access, information disclosure, unsafe update behavior or a
security-relevant trust-boundary failure.

Severity is assessed using impact, exploitability and relevant
CVSS considerations. A reflected parameter, a missing HTTP header
or a static DOM-sink pattern is **not** automatically a vulnerability.

## Safe testing rules

- Test only software, systems and data you own or have explicit
  authorization to assess.
- No destructive actions, denial of service, social engineering,
  phishing, credential harvesting, exfiltration or privacy invasion.
- Do not scan or attack third-party targets as part of a report.
- Use synthetic data and redact logs, credentials and identifiers.
- Stop if your test causes unexpected impact.
- Coordinate disclosure privately; do not publish unpatched details.

## Submission checklist

1. Affected file/module and commit or application version.
2. Short description of the vulnerability and expected behavior.
3. Safe reproduction steps on a local or otherwise authorized setup.
4. Actual impact, preconditions and affected trust boundary.
5. Minimal proof of concept without private data.
6. Suggested mitigation, if available.

Submit privately through GitHub's Private Vulnerability Reporting
feature **if enabled**. Otherwise request a private contact channel
without disclosing exploit details in public.

## Review, rewards and acknowledgment

Reports may be accepted, declined, considered duplicates or returned
for more information. Reward eligibility is discretionary, including
funding and independent verification; no response-time or payment
deadline is guaranteed. Public acknowledgment requires consent.

See [SECURITY.md](../../SECURITY.md) for reporting and trust boundaries.
